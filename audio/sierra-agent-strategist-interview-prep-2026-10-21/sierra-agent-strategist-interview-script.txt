Question six. Walk me through an A I project you built for a customer.

Answer. Pythia is a restructuring analytics system I built for Constellation. A central design decision was to separate evidence extraction from downstream inference. An inferred relationship should not quietly become a documented fact. Question eight. Tell me about a consequential technical decision you made.

Answer. Pythia's provider comparison made the precision and recall tradeoff very concrete. In a development benchmark of sixteen matched documents, one provider produced approximately ninety percent precision and seventy-one percent recall. The other was around eighty percent precision and seventy-seven percent recall. So the model finding more relationships also introduced more incorrect ones. For restructuring research, a false relationship can contaminate the graph and distort subsequent reasoning. That makes the error type matter more than one aggregate score. My approach was to compare the outputs against the same references and inspect their differences. It also suggests a useful design: separate broad candidate discovery from the stricter standard for an evidence-backed relationship used downstream.

Question nine. How did you know whether Pythia was working?

Answer. I used paired comparisons across two providers on sixteen matched financial documents. We compared extracted relationships with reference records and examined false positives and omissions, alongside source lineage and deterministic checks. Keeping the first pass blind to benchmark information helped prevent the answer key from contaminating extraction. This was development benchmarking. Sixteen documents do not establish broad production reliability, and relationships inside one document are correlated. The next step would be a frozen set of new documents, with breakdowns by document type and relationship difficulty. I'd connect that technical quality to whether analysts can verify the output and complete their research task.

Question ten. Tell me about something that did not work as expected.

Answer. In Pythia, a validation rule was rejecting valid creditor relationships because it didn't recognize formal ownership language. The model had already extracted useful evidence, but the guardrail was discarding it. The correction changed the admission rules while keeping the prompt, schema, and model input fixed. On three development documents containing forty-seven reference relationships, one provider's recall rose from about thirteen to eighty-three percent, with no false positives in that test. The decision was to test held-out documents before expanding the change. The lesson is to inspect the whole path from model response to accepted output. A conservative control is only useful if it distinguishes unsupported claims from valid evidence. More prompting would have missed the actual bottleneck.

Question twenty-two. How would you design an agent for someone reporting an unfamiliar card charge?

Answer. I'd begin with the institution's approved process and a narrow scope. The agent should acknowledge the concern, establish the required identity and account context, and retrieve authoritative transaction details. It should clarify whether the customer recognizes the merchant before moving to the permitted dispute or card-protection steps. Consequential actions need explicit confirmation and system-enforced authorization. I'd design for duplicate requests, unavailable systems, and a customer whose situation doesn't fit the standard path. The handoff should preserve the relevant facts so the customer doesn't start again. Success means the appropriate action was completed and explained accurately. I would work with the institution's specialists on policy, rather than let the model improvise requirements.

Question twenty-three. When does an agent need retrieval, and when does it need tools?

Answer. Retrieval can provide the relevant policy or product explanation. A tool connects the agent to current account state or lets it perform an authorized action. Both may be needed in one conversation. For a card replacement, retrieved policy might explain delivery options, while a system interface confirms the address and creates the order. I'd keep critical validation in the service that performs the action. The model can interpret intent, but it shouldn't be the final authority on permissions or transaction rules. I'd also verify the result before telling the customer the action succeeded. A timed-out request may have completed, so retries need a way to avoid creating duplicates.

Question twenty-four. What does good context engineering mean to you?

Answer. It means giving the model the right evidence and state for the current decision, with clear boundaries around what it can trust. For a customer agent, I would separate the customer's statements, authenticated account facts, current policy, and prior tool results. I'd retrieve only relevant information and preserve where it came from. Older conversation summaries should not override a current system response. I would also treat text from documents or users as data, rather than authority to change the agent's instructions. Pythia reinforces that discipline because extracted facts and inferred relationships have different evidential status. More context is not automatically better; irrelevant or contradictory material can make a response less reliable.

Question twenty-five. How would you evaluate a new customer-facing agent?

Answer. I'd create a test set around real customer journeys, with ordinary cases, difficult exceptions, and prohibited actions. I'd check whether the agent completed the correct task, followed policy, communicated clearly, and escalated when appropriate. For tool use, the final system state matters as much as the conversation. I'd combine deterministic checks with expert review, using model-based grading only after checking its agreement with human judgments. Because behavior varies, I'd run important scenarios repeatedly and report results by risk category. I'd keep a separate release test set and add production failures to regression testing. One overall pass rate can conceal an unacceptable failure in a rare but consequential workflow.

Question twenty-six. How do you decide whether an agent is ready to launch?

Answer. I'd agree on release criteria before looking at the final results. Those criteria should reflect the task's risk and distinguish ordinary quality issues from failures that block launch. I'd want representative test coverage, reliable integrations, tested escalation, clear monitoring, and an owner who can intervene. I would release to a limited population first and compare the results with the existing process where feasible. The release should be reproducible, so we know which model, instructions, knowledge, and tools produced it. If something goes wrong, we need a tested way to restrict the agent or revert the change. Launch readiness is a combination of measured behavior and operational readiness, rather than a model score alone.

Question twenty-seven. An agent's performance suddenly deteriorates. How would you investigate?

Answer. I'd first assess customer impact and contain any serious harm. Then I'd examine what changed: the model, instructions, knowledge, an interface, customer mix, or the way we measure success. I'd inspect representative failed conversations and tool traces, grouping failures by type rather than relying on anecdotes. I'd also check whether the problem is concentrated in a particular journey or customer segment. Once we have a hypothesis, I'd reproduce it in a controlled test, apply the smallest useful correction, and rerun relevant regression cases. Throughout, I'd give the customer a concise update: what we know, what we're doing, and when they'll hear from us again. Confidence should follow evidence, not the pressure to sound certain.

My aim would be to improve those customer outcomes while checking for tradeoffs in risk, repeat contacts, and operating cost.
